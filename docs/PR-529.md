# keychron: CKBT51 link hardening + 133 Hz report rate

## Summary

Three focused commits improving Bluetooth reliability and report rate on
Keychron CKBT51-based boards (K Pro / Q Pro family):

1. **`bluetooth/`**: UART parser hardening, report-queue resynchronisation on
   link loss, low-power gate, connection retry pacing, optional fast wake.
2. **`keychron/*/`: module parameters** — `report_rate` 90 → 133 Hz and
   `reconnect_timeout` 5 s → 60 s for all CKBT51 boards (uniform, mechanical).
3. **`k13_pro/`**: wider module parameter-init window, documented LPM tunables,
   debounce experiment note.

Scope: `keyboards/keychron/**` only. LKBT51 (separate SPI stack) is
intentionally untouched. No JSON/PID/layout changes; default behaviour is
unchanged except for the two module parameters above.

## Motivation (field symptom)

A K13 Pro (ISO RGB, Linux host, Intel AX210) intermittently produced bursts of
repeated keystrokes and "silent" reconnections, typically after short idle
periods. Root-cause analysis of the QMK side found:

* The report queue was only flushed on `EVT_DISCONNECTED`. If that event was
  lost (UART overrun after STOP1 wake), the STM32 kept queueing while the link
  was down, and the backlog was drained at ~3 ms/report after reconnection.
* `ckbt51_task()` copied up to 255 bytes into a 32-byte stack buffer with no
  length check (a 64-byte frame is a *valid* `GET_MODULE_INFO` response).
* `lpm_task()` allowed STOP1 with reports/retries/events still pending.
* Every keystroke sent while disconnected issued a `connect` command (3 ms
  blocking busy-wait each), causing reconnect churn.
* `ckbt51_param_init()` only ran if the module booted within 1 s of MCU
  startup; otherwise `report_rate`/`reconnect_timeout` were never applied.
* `reconnect_timeout = 5 s` meant the module gave up reconnecting after 5 s.

## Changes

### Commit 1 — `bluetooth/`
* Bound the RX frame to `PACKET_MAX_LEN` (64) with `3 <= len <= 64`, chunked
  `ckbt51_dfu_tx` (7+25 then 1+31 bytes) so legitimate frames are not dropped
  and the stack buffer cannot overflow.
* Flush the pending report queue on `EVT_RECONNECTING` as well as
  `EVT_DISCONNECTED` (prevents backlog replay after a lost disconnect event).
* Reset the retry timer on `ACK_FIFO_FULL_ERROR` (no immediate resend storm).
* `lpm_task()`: do not enter STOP1 while the report queue, a retry or the
  event queue is non-empty.
* `bluetooth_connect()` rate-limited to one attempt per 500 ms (the first
  attempt is always immediate).
* Removed the dead `bluetooth_report_protocol` variable.
* Optional `CKBT51_FAST_WAKE` (compiled out by default) to skip the 3 ms INT
  wake sequence when the module was active recently.

### Commit 2 — module parameters (25 boards)
`report_rate` 90 → **133 Hz** (documented maximum) and
`reconnect_timeout` 5 → **60 s**. `connected_idle_timeout` (7200 s) and
pairing values are unchanged.

### Commit 3 — `k13_pro/`
Parameter-init window widened 1 s → 5 s (slow module boot), LPM tunables
documented in `config.h`, `DEBOUNCE_TYPE=asym_eager_defer_pk` recorded as an
opt-in experiment only (not enabled).

## Measurements (K13 Pro ISO RGB, BT, Linux 6.12/AX210)

Tap test (`uinput` tap timing, single key, 10 s, n=150–312 taps):

| Metric | Before | After |
|---|---|---|
| Minimum inter-report gap | 7 ms | **5 ms** |
| Estimated report ceiling | ~143/s | **~200/s** |

Expected, but **not yet claimed as fixed**: the burst symptom requires 2–3 days
of field use to confirm. `btmon` capture instructions are included in the
companion analysis for any remaining episode.

## Testing

* `qmk compile` for `k13_pro/{ansi,iso}/{rgb,white}` (default + via) and
  `k14_pro/ansi/rgb`: all pass; flash usage ≈ 24 % of 256 KB.
* `qmk test-c`: 77 suites passed, 0 failed (not triggered by CI for
  `keyboards/**` changes).
* `qmk format-text` with clang-format **19.1.7** (same as CI container):
  zero diff.
* `qmk lint` for the changed keyboards: only the pre-existing findings in this
  branch (`empty variant rules.mk`, `via` keymap header, `iso/rgb/rgb.c`
  license header) — none introduced by this PR.
* Flashed on hardware via ROM DFU; configuration backed up and restored with
  Keychron Engine before/after.

## Known limitations / follow-ups (not in this PR)

* Toggling BT → USB → BT in under 500 ms can suppress one `connect` attempt
  (one keystroke may be lost until the next fallback).
* Parameter init still runs only at first BT init per boot; switching to BT
  long after boot leaves the module on its defaults (follow-up: one-shot flag
  instead of the uptime window).
* Post-LPM module state resync (`CKBT51_CMD_READ_STATE_REG`) needs the module's
  register semantics — deferred pending vendor documentation.
* Per-key debounce (`sym_defer_pk`) and `CKBT51_FAST_WAKE` need hardware
  validation before being enabled.
